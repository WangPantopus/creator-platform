# W4 commerce implementation and recovery

This is an implementation register, not paid acceptance. [Current acceptance](../status/W4.md) and [producer contracts](../coordination/W4.md) are authoritative about outstanding integrations. All amounts are safe integer minor units with explicit currency; aggregation/allocation uses integer arithmetic. Public client routes never accept settlement/refund/payout evidence or credit issuance amounts.

## Access, memberships, pass and money

- `access/commerce.ts` computes one effective equivalent grant, includes capabilities/source/state/counters/shared pass budget in its version, and reserves actual configured cost units. W3 must persist the distinct reservation ID and consume or release it with durable generation outcome. Paid/trial AI activation is gated until this integration exists.
- Membership billing uses one fan/currency/customer consolidated account, effect keys, confirmed paid invoice line allocation and immutable receipt/usage history. Current-period first use survives replay; a new paid period starts a new usage window. Immediate unused-seven-day/prorated cancellation computes from the actual paid receipt. Card authentication remains processing until verified invoice truth. Actual Stripe Billing and store server adapters, catalog, tier editing/change and payment/proration policy are incomplete.
- A terminal consolidated subscription is never reactivated. A new subscription can bind only after verified old termination/no live lines, under the same customer/account and a fenced start effect. Purchase histories retain old items; provider references cannot move accounts. Aggregate version fences reject older active truth after cancellation/refund.
- StoreKit purchase/restore uses the genuine OS transaction, account token and configured products; transaction finishing follows server verification. Local receipts never grant access. Store reconciliation also fences the original purchase version/period and rejects same-period refunded access restoration; paused/restricted creator cleanup can revoke grants. Android's Play Billing client and both server notification/catalog verifiers are not yet delivered.
- Pass period comes from a verified account-bound purchase, ends on UTC calendar-month boundary and does not refill on replay/free replacement. Pass is locked before slots; current/draft/ended/replaced history is preserved. An incomplete next-cycle draft carries current choices. Membership-included AI uses no slot. A new purchase reference needs provider-verified old terminal lineage and a non-overlapping cycle. Shared used/reserved counters survive same-cycle restoration. Prorated paid checkout and real pool provider adapter are missing.
- Pool allocations use exact active slot seconds and configured net pool receipts, integer floor/remainder, immutable causes and creator-cycle serialization. Credits use configured currency/per-read/cap, trusted deduped read evidence, a noncash wallet and verified checkout allocation; refunds may revoke issued credits according to explicit policy. Refund/read issuance share wallet/commitment locks. W7 qualification and genuine checkout integration remain open.
- MoneyReconciliation accepts genuine current cash/fee/reserve/dispute provider statements, checks append-only cash and net totals, and fences on both packet and commitment versions. A stale no-dispute response cannot clear a newer hold. CreatorSettlement reads actual KYC/country/provider funds and due/dispute/ledger state; transfer/reversal keys and compensation are durable. No actual onboarding/Connect/tax/country/statement/pool adapter is configured.

## Transaction and recovery contract

Mode readers acquire shared `commerce.mode:<id>` transaction advisory locks, writers acquire exclusive before row/capacity/packet/share locks. This preserves fan SELECT while creator-only UPDATE RLS remains enforced; PostgreSQL FOR SHARE would apply UPDATE RLS and hide offers. Tier writers must use exclusive `commerce.tier:<id>` matching fan reads. Billing account precedes membership; pass precedes slot. Provider I/O is outside SQL locks. Reconciliation captures aggregate versions before I/O and rejects intervening changes rather than restoring stale access.

Durable payment, billing and payout effects have scoped idempotency/provider keys, pending/processing/unknown/done/failed states, a lease and incrementing attempt. Completion/error writes require the current attempt/processing claim. A worker that lost its lease cannot overwrite newer state. Repeated commands require the same canonical body for the same actor/operation/key. An ambiguous external result is processing until current provider truth or explicit scoped operations resolves it.

`payments/inbox.ts` mounts raw HMAC-verified Stripe events before JSON parsing, stores only provider/event/type/object references and dedupes by provider/event. `CommerceRecoveryWorker` supports packet, billing, pass and payout work scopes; packet deadlines are a separate dispatch. W8 must supply the real purpose-bound scope issuer, register providers/jobs, and provision least-privilege inbox SELECT/UPDATE; current app role has inbox INSERT only. There is no automatically running commerce worker in this increment.

Operator recovery:

1. Use a live W8 case/job with exact packet/creator/account scope; do not impersonate an unrestricted creator or edit ledger history. Refresh current provider intent/subscription/refund/transfer and original effect key before deciding.
2. Recover expired processing leases through the registered worker. Fetch current truth first for known references. Replay only the original idempotent provider operation while its documented dedupe window is safe; aged unknown operations require provider/operator reconciliation, not a fresh payment key.
3. Verify packet authorization lineage, exact amounts/currencies and ledger causes. Confirm capture/refund before fulfillment, entitlement, payout or case completion. `commerce.full_refund`/`partial_refund` throw for pending/unknown outcomes until their exact refund ledger cause exists.
4. Reconcile membership/pass/account version and paid period. Reject stale provider responses and refetch. Preserve spent/reserved allowance and immutable receipts/usage/purchase history; never grant from a client receipt or reset same-cycle counters.
5. Reconcile money statement, dispute hold, delivery+7-day release and actual provider account availability. If transfer succeeded while eligibility changed, reverse it with the stable compensation key; leave unknown until reversal is confirmed. Append a new adjustment cause; do not rewrite prior entries.
6. Publish outbox invalidations/notices using current scoped state and minimal recipient references. Verify the consumer card/capability and multi-client refresh; worker completion alone does not prove delivery.

Privacy export includes scoped packets/commitments, linked access grants/counters, authorization/sharing/read/effect records, and account/creator financial records including null-packet ledger, memberships/receipts/use, pass/slots/budget, credits/trials, spending/billing/purchase/payout/event records. Each bounded collection reads 2001 and throws above 2000; W8 stores the resulting artifact under its own size/purpose fence. No successful truncated export. Account deletion acknowledgment is disabled pending Q16 financial retention/refund consequences. Operational authority and paginated large export/deletion implementations are still dependencies.
