# Platform inventory and runtime completion gaps

Research date: 2026-09-29 (America/Los_Angeles). This is a read-only audit of the current repository and local tool/device inventory. Only this document was written. No app was launched, no provider was configured, no database was changed, and no new test code or unit tests were run for this audit. Historical checks below are reported from existing evidence, not repeated here.

The implementation stack is Node.js/TypeScript for the backend, Next.js for web, native Swift/SwiftUI for iOS, and native Kotlin/Compose for Android. React Native/Expo references in the source architecture are superseded by the user's explicit native instruction. Build here first; later Pantopus integration is an adapter workstream. `Qelvora` remains a replaceable placeholder, with Pantopus retained as the identity provider name.

## Current product reality

The 53 component implementations are reusable UI foundations. They do not establish 53 completed screens, a working signed-in application, a live AI conversation, or store readiness. Both native release hosts currently show Welcome; most component actions are callbacks waiting for a domain host. The web has three foundation screens and a reference gallery. The configured backend seam has durable conversation and signing primitives, but the default executable has no configured identity or generation provider.

## Manual evidence and verification contract

No new unit, UI or integration test code is proposed. Owners build the app, exercise actual workflows against real configured boundaries, capture evidence and fix observed defects. A missing provider/device is recorded as blocked/unavailable, not passed. A provider sandbox is real provider verification for its declared scope; it does not prove production payout, real-money settlement or store review.

Evidence record per scenario: owner/W-ID; source revision or shared-checkout snapshot; exact app build/version and backend contract revision; platform/OS/device model; environment and provider mode; sanitized setup/steps; expected design/domain behavior; observed result; screenshot/video and permitted redacted server/provider event IDs; fix reference and repeated manual result; remaining limitation. Do not include access tokens, raw private fan text, secret URLs, personal device identifiers or provider credentials. Store each run under an owner-specific `artifacts/manual/Wn/SCENARIO/RUN-ID/` with a concise Markdown record; acceptance records go to the owner's workstream document rather than the shared BUILD_LOG.

## Parallel work plan for three to eight agents

The following uses the authoritative provisional W1–W8 names. They are product workstreams, not a split into web-only versus mobile-only teams. Domain owners deliver their feature contracts and applicable behavior on all required clients. Root/integration owns sequencing and shared-files arbitration. The current multi-agent runtime exposes **four slots including root**, so the immediate executable arrangement is root plus three workers; six/eight are later capacity configurations, not a promise that this session can spawn eight at once.

Suggested staffing:

- **Four total agents (current four-slot limit):** worker A W1, worker B W2 with W5 setup dependencies, worker C W3 with W4 interface-first lifecycle; root W8 integration/research/arbitration. W4 full implementation and W5 fulfillment run in the next independent batch once contracts are pinned; W6/W7 planning runs in queued batches without requiring live auth/device access. Keep active workers to disjoint directories.
- **Three total agents:** A W1+W8 coordination, B W2+W5, C W3+W4; stage W6/W7 after identity/conversation/commerce seams. This sacrifices simultaneous feature count to preserve a working vertical slice.
- **Five total agents:** dedicate workers to W1, W2, W3 and W4; root carries W8 integration and queues W5/W6/W7 planning or implementation. Freeze shared interfaces before domains simultaneously integrate them.
- **Six total agents:** W1–W5 each get a worker; root owns W8 and stages W6/W7. **Seven total agents:** add a dedicated W6 call/media owner; root carries W7 sequencing until notification capacity exists. Delay live call acceptance until physical device leases and a real provider exist.
- **Eight total agents:** workers own W1–W7 and root owns W8 plus integration arbitration. This maximizes source work, not simultaneous emulators, migrations or provider accounts. The same leases and shared-file rules still apply; there is no ninth coordinator assumed.

The safest early integration milestone is one creator/fan pair with real identity, approved AI sentence delivery, process-restart replay and a signed human reply through the actual web/iOS/Android app hosts. This does not replace the full-build scope with a proof-only product; it makes interfaces concrete while the remaining workstreams progress in parallel. Follow with membership/entitlement and request fulfillment, then notification/media/call slices and pilot release evidence.

### File and contract ownership

Root's shared contract/ownership/lease guidance is authoritative when published. Recommendations for that guidance:

1. Assign **one writer per existing file**. Shared-owned files: root/package manifests and lockfile, generators, brand/copy/tokens, `packages/api` schemas/OpenAPI/codegen outputs, app entrypoints, Xcode `project.yml`, Android manifest/build settings, root layout/router, CI and aggregate BUILD_LOG. Feature owners request additions by exact key/schema/route contract; the integration owner performs them once. Never hand-edit generated native files.
2. Feature source directories should be disjoint (`modules/<domain>`, web route/feature directories and native `Features/<domain>` namespaces). A shared native component change has its current owner; coordinate callers separately. All Swift sources compile in one module today, so public name/type collisions still require the contract registry even with separate files.
3. Pin a minimal typed contract before parallel implementation: opaque actor/session, feature capabilities/readiness, route destination including return context, author states, consent version, thread scope, idempotent commands, cursor/epoch/generation checkpoint, money minor units/currency, error categories and server timestamps. Domains publish additive revisions; no silent schema widening or status strings invented in clients.
4. One migration writer/dispatcher assigns monotonically ordered migration numbers. Domain authors propose schema/data changes in their own files; W8/integration orders application and verifies compatibility in a dedicated database. No concurrent whole-schema migrations against a shared DB and no owner/service-role application runtime.
5. Every workstream hands off implementation, manual evidence, observed defect/fix, changed contracts and unresolved decisions. A source component count or passing compile does not mark a product acceptance row complete. Provider-unavailable states stay explicit until actual integration is demonstrated.

### Build, database and device leases

| Shared resource | Collision prevention |
| --- | --- |
| Source/lockfiles/codegen | Root serializes shared mutations and generated resources. Stop concurrent installs/renames/project generation. Use a short source-stability barrier before an integrated build. Shared-checkout agents do not checkout/reset/stash or overwrite other agents' edits. |
| Node/Next | Lease concrete port pairs; Next's existing script uses3000 and writes `.next`, so only one process/build owns that app output in the shared checkout. Independent ports require isolated output/worktrees or serialized runs. Distinct service instance does not imply distinct DB or provider state. |
| Swift/Xcode | Each build gets distinct DerivedData; shared Swift Package `.build` and project generation remain one-writer resources unless isolated explicitly. One simulator lease for install/launch/permissions/theme/capture. Mac snapshot executables are historical aids; no new automated tests in this plan. |
| Gradle | `apps/android/app/build`, `.gradle`, generated resources and artifact paths are shared. Serialize Gradle in this checkout; project-cache flags alone do not isolate `app/build`. Separate authorized worktrees can isolate source/output but do not isolate a running device/provider. Never run concurrent record/connected/build tasks in the same tree. |
| Postgres | Allocate one dedicated development DB per independent destructive/manual scenario; distinguish migration-admin versus non-owner runtime URL without printing credentials. Lease each DB and seed namespace; initial migration/global roles/extensions still need one coordinator. Never use the prior unit-test fixture or Pantopus production DB as an implicit shared sandbox. |
| Emulator/simulator | Lease by exact UDID/serial and owner/run/time window. Device state mutations, global ADB operations and snapshot restore are serialized. One iOS + one dedicated Android device can be reviewed concurrently; extra source agents queue for those boundaries. Never kill/reset other creator or Pantopus sessions. |
| Providers/store sandboxes | Give each run isolated test actors, products/environment and idempotency/event namespace; no competing edits to the same dashboard webhook/configuration. W4 owns money scenarios, W6 call rooms/recording; W8 coordinates cross-provider outcomes. Sandbox account actions and live production actions are not interchangeable. |
| Evidence | Owner/run-specific paths; no rerecording accepted/reference images as a shortcut. Keep device/runtime/design/provider evidence distinct. Redact secrets and personal content before sharing. |

Integration cadence: agree contracts and ownership at each batch start; domain owners publish readiness/contract changes promptly; root regenerates once, integrates entrypoint wiring and runs an app build after a source-stability checkpoint. Then reserve a short manual vertical-flow slot on each real host, record evidence and fix the responsible feature. Do not let unconfigured adapters convert an end-to-end requirement into a passing mock. At the next checkpoint, retest the affected real flow after fixes and record limitations; broaden runtime verification when new dependency/platform behavior warrants it. Provider selection or an unavailable physical device is an explicit decision/resource dependency, not a reason to label a full slice shipped.

## Risks most likely to be overlooked

- Release host wiring remains almost entirely absent despite a complete component list; the default web auth destination is not implemented, and native authenticated callbacks currently have no navigation action.
- Checkpoint serialization is not checkpoint persistence. Cursor, epoch, generation sequences and rendered timeline must commit together; account/rights changes must purge or invalidate local data, not just reconnect the socket.
- Product rename can change display strings easily, but app IDs, passkey RP/domain, App Links signing certificates, push environments and store product identities must remain deliberately stable or receive a migration plan.
- Android14 fixture/runtime checks miss API36 release behavior. Android26 minimum and API28 passkey availability also need a product-visible signing boundary.
- A single generic payment path cannot be assumed for memberships, asynchronous personal fulfillment and live calls. Client success, webhook arrival and final entitlement/ledger truth are separate boundaries.
- Ordinary chat notifications and VoIP calls have different platform constraints. Scheduled call ending, participant reconciliation and money outcomes require durable server jobs even if the provider/media UI appears connected.
- Permission prompts, lock-screen metadata, caches, downloads, backups, analytics and provider traces are additional disclosure surfaces. Thread RLS alone does not constrain all of them.
- Existing components contain intended disabled/unavailable controls until real providers exist; enabling those callbacks without their authority, readiness and failure contract risks a convincing UI that performs no authorized act.
- Shared emulator, `.next`, Gradle output, generated files and DB/provider scenarios are scarce resources. Eight source owners cannot safely perform eight simultaneous runtime verifications on two shared phones.
- A local debug build and macOS/Paparazzi baseline do not establish native design acceptance, physical power/audio reliability, signed release upgrades, provider settlement or a functioning external pilot.
