# W6 C2PA runtime adapter

`apps/backend/src/modules/media/credentials.ts` supplies the concrete `C2PAToolCredentialSigner` consumed by either media worker's existing credential interface. It is implemented but remains unconfigured and has no successful creator signing/publication acceptance. It does not provide W1 passkey authority, consume another signature, authorize publication, mark AI audio, or activate a capability.

The host must supply all six configuration fields: absolute `executable`, absolute `signerExecutable`, absolute `trustAnchorsFile`, its exact `trustAnchorsSha256`, an absolute private `workingDirectory`, and a positive approved `maxBytes` within the transport ceiling. Provision a current official trust-anchor file through W8 custody; pin its actual digest and refresh that configuration when the list changes. The working directory belongs exclusively to the bounded ingestion pool, with private permissions and no interactive/API access. The external signer implements c2patool's info/sign protocol and manages its own HSM/KMS authentication and keys. Its executable path cannot contain whitespace because the CLI accepts a command string. Never substitute the bundled test certificates or the `/usr/bin/false` failure diagnostic for that signer.

The adapter deliberately pins **c2patool 0.28.1** and its report contract. Updating the tool requires checking its matching signing, settings and validation documentation and verifying the affected runtime paths. Runtime supply and executable integrity remain W8 responsibilities. Inherited `C2PA_*`/`C2PATOOL_*` settings are removed; each invocation uses private explicit settings and the pinned anchors. Thumbnail generation and remote-manifest fetching are disabled. Signature, certificate/timestamp trust and OCSP verification remain enabled. W8 must supply appropriate egress for the configured signer, timestamp service and certificate-status endpoints.

The exact worker manifest is embedded in `org.pantopus.creator.media`. That assertion binds the immutable processed bytes/hash/MIME/duration and all existing account, creator, object/thread, asset/version and consumed-act fields. No display-brand constant becomes a signing identity. The platform certificate is separate from the creator's W1 passkey act.

Before signing, bounded descriptor reads verify the actual processed tuple and copy it into a private typed `.m4a` or `.png` file. Signing and independent readback are separate CLI invocations. Verification requires one active manifest, the exact assertion payload, no ingredients or validation failures, and positive signature validity/inside-validity, certificate trust, assertion-hash and data/BMFF binding statuses at the active manifest's own URLs. An explicit report format must match; its omission is accepted only for claim-v2, which omits dc:format, while the exact signed MIME tuple and file binding remain mandatory. The first platform credential uses `--create empty` rather than inventing a parent ingredient or platform camera capture. The report's `Valid` state and the assertion's own `c2paVerified` field are insufficient. The original processed copy is checked again after signing; the returned credentialed bytes retain their separate delivery identity. The existing worker still enforces the purpose's byte ceiling, lease/version fence and actual publication authority.

October1 continuation adds [development-only credential provisioning and signer tooling](../../infra/local/w6/README.md). Genuine CLI readback under its generated root succeeded for a synthetic component; untrusted and altered-audio reports were rejected. [Evidence](../../artifacts/workstreams/W6/human-media/2026-10-01/README.md) preserves that limited scope. This is development trust, not production KMS/trust-list qualification or accepted human publication.

Commands have bounded output/deadlines, discard potentially sensitive stderr, and terminate their Unix process group on timeout/abort. Cleanup waits for process termination before removing staging. Nonblocking descriptor opens reject non-files without waiting for a FIFO writer; staging reads/writes honor the credential job's abort signal. Temporary directories are removed on success and failure. The adapter never mutates the original processed file.

Personally executed diagnostics used the genuine official tool and its **existing** untrusted `sample/C.jpg`, without signing anything with its bundled keys. The tool returned `validation_state: Valid` and `signingCredential.untrusted`; the adapter rejected it. A genuine CLI call with an executable that exits unsuccessfully also rejected, preserved the input digest and removed its private staging directory. These are failure diagnostics, not successful production signing or human media acceptance. See [evidence](../../artifacts/workstreams/W6/completion/2026-10-01/README.md).
