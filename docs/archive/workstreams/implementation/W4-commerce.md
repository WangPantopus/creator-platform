## Transaction and recovery contract

Mode readers acquire shared `commerce.mode:<id>` transaction advisory locks, writers acquire exclusive before row/capacity/packet/share locks. This preserves fan SELECT while creator-only UPDATE RLS remains enforced; PostgreSQL FOR SHARE would apply UPDATE RLS and hide offers. Tier writers must use exclusive `commerce.tier:<id>` matching fan reads. Billing account precedes membership; pass precedes slot. Provider I/O is outside SQL locks. Reconciliation captures aggregate versions before I/O and rejects intervening changes rather than restoring stale access.

Durable payment, billing and payout effects have scoped idempotency/provider keys, pending/processing/unknown/done/failed states, a lease and incrementing attempt. Completion/error writes require the current attempt/processing claim. A worker that lost its lease cannot overwrite newer state. Repeated commands require the same canonical body for the same actor/operation/key. An ambiguous external result is processing until current provider truth or explicit scoped operations resolves it.

`payments/inbox.ts` mounts raw HMAC-verified Stripe events before JSON parsing, stores only provider/event/type/object references and dedupes by provider/event. `CommerceRecoveryWorker` supports packet, billing, pass and payout work scopes; packet deadlines are a separate dispatch. W8 must supply the real purpose-bound scope issuer, register providers/jobs, and provision least-privilege inbox SELECT/UPDATE; current app role has inbox INSERT only. There is no automatically running commerce worker in this increment.

Operator recovery:

1. Use a live W8 case/job with exact packet/creator/account scope; do not impersonate an unrestricted creator or edit ledger history. Refresh current provider intent/subscription/refund/transfer and original effect key before deciding.
2. Recover expired processing leases through the registered worker. Fetch current truth first for known references. Replay only the original idempotent provider operation while its documented dedupe window is safe; aged unknown operations require provider/operator reconciliation, not a fresh payment key.
3. Verify packet authorization lineage, exact amounts/currencies and ledger causes. Confirm capture/refund before fulfillment, entitlement, payout or case completion. `commerce.full_refund`/`partial_refund` throw for pending/unknown outcomes until their exact refund ledger cause exists.
4. Reconcile membership/pass/account version and paid period. Reject stale provider responses and refetch. Preserve spent/reserved allowance and immutable receipts/usage/purchase history; never grant from a client receipt or reset same-cycle counters.
5. Reconcile money statement, dispute hold, delivery+7-day release and actual provider account availability. If transfer succeeded while eligibility changed, reverse it with the stable compensation key; leave unknown until reversal is confirmed. Append a new adjustment cause; do not rewrite prior entries.
6. Publish outbox invalidations/notices using current scoped state and minimal recipient references. Verify the consumer card/capability and multi-client refresh; worker completion alone does not prove delivery.
