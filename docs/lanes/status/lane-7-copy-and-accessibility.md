# Lane 7: copy lookups (WP 7.10) and accessibility (WP 7.11)

Written by lane 7. One spec for both apps; a difference between the platforms is a defect. E7.10 in
the brief covers both packages: no literal user-facing strings outside copy lookups (scan the
source), none of the forbidden words, VoiceOver and TalkBack read authorship first, the largest
text, contrast in both themes.

## WP 7.10: copy lookups

### Rules

1. **Every word a person reads comes from `config/copy.json`.** Swift calls
   `QelvoraCopy.text("key", values:)`, Kotlin `QelvoraCopy.text("key", mapOf(...))`; both are
   generated by `pnpm generate`. A sentence built from pieces becomes one key with placeholders
   (`"{name}'s account"`), so the words stay together and the order can change in one place.
2. **One element, one key, on both apps.** Where the two apps said different words for the same
   element, they now say the same words (decisions below).
3. **Existing keys are reused only where they mean the same thing** (`close`, `retry`, `back`,
   `report`, `conversationAccess`, `sensitiveMemory`, `approvedAuthor`, `stepIn`, the P5 `picker…`
   keys and 18 more). Every other text has a new `native…` key holding the exact words the app
   showed before. The 527 new keys are one block at the end of `config/copy.json`.
4. **Not copy, so still literal:** protocol values (HTTP methods and headers, server texts the app
   matches such as "Answered publicly.", realtime close reasons), routes, date patterns, regular
   expressions, ids that build keys (tab raw values, the team workspace's key suffixes, Discover's
   categories), developer diagnostics that are thrown and never shown, and the debug-only design
   catalog with its sample content ("Maya", "Kiln Club members"). The scanner lists each of these.

### Decisions taken as the proposed default (2026-10-16; the founder may veto any)

The wording closest to the web's was taken; otherwise the more complete one.

| Element | Was (iOS / Android) | Now, both apps |
| --- | --- | --- |

### Parity defects found, not fixed here (structure, not words)

Each keeps its own keys until it is fixed; 7.11 takes the ones that are about controls.

- **Privacy screen** (`W3PrivacyScreen` / `ConversationPrivacy`): the sections are in a different
  order; iOS shows "The creator and their team can see these memories …", Android does not; an
  access row is three lines on iOS and one text on Android; off the record and sharing the intro
  are toggles on iOS and buttons whose label changes on Android (7.11).
- **Spending**: a toggle "Remind me at 50% and 100%" on iOS, a button "Reminders at 50% and 100% ·
  on/off" on Android (7.11); the amount field is "Monthly amount" with the placeholder "Amount in
  {currency}" on iOS and "Monthly amount in {currency}" on Android.
- **Feedback, data scope and report type**: pickers on iOS, rows of buttons with a combined label
  on Android (7.11).
- **Public handle**: a label and a hint on iOS, one description on Android (7.11).
- **You**: "Memory and access" is a row with the creator's name as its detail on iOS and a button
  "Memory and access · {name}" on Android.
- **Empty states**: requests and memberships have a title and a body on iOS; Android shows one line
  for requests and only the title for memberships.
- **Access screen**: iOS lists each human mode with what is left and its price; Android does not.
- **Signing passkeys** (Studio): registration errors are handled differently.

### Ticket

- **Lane 3** (`apps/web/features/conversation/ConversationScreen.tsx`, `AccountScreen.tsx`,
  `ComparisonChoice.tsx`): the web's own literals for the same elements differ again (for example
  "… without sending a duplicate.", "It's still labeled, still visible …"). The native keys now
  exist in `config/copy.json`; using them would make the three surfaces say the same thing.
