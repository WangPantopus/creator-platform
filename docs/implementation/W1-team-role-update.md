# Current Team role replacement

The existing identity Team API now exposes POST `/v1/identity/{creatorId}/team/{accountId}/roles`. Its required `X-Expected-Account-Id` is the original identity mismatch precondition; it never supplies account authority. The strict `TeamRolesUpdateInput` contains distinct, nonempty `expectedRoles` and `roles` sets from the four existing Team roles. The response is the existing `Done`. Canonical OpenAPI and shipping Swift/Kotlin clients are regenerated; the original same-origin web identity proxy admits exactly this path.

The configured router reuses the actual session middleware Actor. The operation holds the original request session, same-client restoration and actual creator denial before positive creator/membership locks. Only the current owner with verified, recovered creator identity may replace an active member's roles; Team roles cannot replace creator identity or approve a named act. Missing current authority refuses 503. The existing creator/member advisory lock serializes invitation acceptance/removal with role replacement. A removed membership refuses 409. Changed reviewed roles refuse `team_roles_changed` 409 unless the desired set is already current, allowing an interrupted successful request to be retried. This compares current role sets, not a fabricated history version or ABA detector.

Successful replacement and an already-current retry revoke outstanding unaccepted invitations for that member, so their old roles cannot be restored by a later acceptance. Accepted invitation history remains intact. Current creator denial/restoration and the opaque original request session are rechecked before the original identity transaction commits. No schema migration, held purpose, creator proof, signature or consent is created.

Canonical generation verifies 12 resources and 116 operations; backend/web types, scoped lint/format and all nine existing backend contracts pass. The existing PostgreSQL integration suite was skipped without its explicit test database; it is not credited. Positive creator/Team operation, owner UI consumption, shipping native compilation/operation and full H08 invite/accept/remove/expiry/race acceptance remain open. Current original Team CRUD is not claimed to acquire these new route bookends merely because it shares a class.
