# W3 offline content: required canonical authority

Read-only consumer proposal at integrated main `1c11b098c3f86ec07740c760b423c4fccc9ec5f7`. This does not implement a cache, grant offline access, select a retention period or approve a capacity.

Current web `ConversationScreen.tsx` stores cursor/epoch metadata in sessionStorage. Swift `W3ResumeStorage.swift` stores bounded account/scope-digested cursor/epoch metadata in Keychain; Android `ConversationResumeStorage.kt` encrypts the equivalent metadata through Android Keystore. Current sockets resume from a newly authorized page. These stores contain no conversation content and do not satisfy package H. Existing account purge hooks must remain in the same canonical sign-out/account-change path.

Before persisting private content, W1/W8 must publish a genuine current-authority operation returning the authorized account, exact creator/fan/thread family, allowed content identities and versions, authority/policy version, issuance and finite expiry, and explicit cache eligibility. It must state which changes invalidate content: account change/sign-out, family deletion, consent withdrawal, creator/source/version/license revocation, human approval correction and lifecycle denial. A session token, cursor, old page or successful API response alone cannot issue that authority.

The producer must decide how revocation while disconnected bounds use of an already issued lease, how time rollback or uncertain expiry is handled, and which retained original/signature/translation/media objects are eligible. No timeout, cache size, stale grace period or retention default is proposed here. An expired or unverifiable proof must conceal its contents until canonical reauthorization succeeds. Reconnect must validate authority before displaying fresh content or dispatching any action.

Once the producer exists, W3 will consume it in the existing clients, encrypt persisted content with account-bound keys, bound records/bytes using the approved limits, distinguish an authorized stale view from current data, retain immutable original proof, and invalidate both content and keys through existing purge hooks. Web storage needs an explicit reviewed encryption/key-lifetime contract; native resume-metadata keys must not silently become content-cache authority. Offline sends remain unavailable and no memory, consent or payment mutation is authorized from cached state.

Required personal acceptance then covers an actual licensed thread on all three clients: authorized bounded content offline, original/version labels, expiry and clock uncertainty, wrong account and creator/fan family, deletion/consent/source revocation, correction, sign-out/key purge, process restart, reconnect and attempted offline send. Current unavailable/reconnect screenshots prove only denial/recovery behavior. No offline-content acceptance is claimed.
