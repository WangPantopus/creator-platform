# Reviewed development role boundary

The development Trust helper defaults to exact `creator_runtime`. An explicitly configured `TRUST_CORE_DATABASE_ROLE` can name a separate loopback request login that inherits only `creator_runtime` and `growth_runtime`. Startup inspects every reachable membership, including non-inherited SET ROLE paths; rejects superuser, bypass, database/role creation, replication, domain object ownership and extra memberships; and refuses extra direct relation, column or function privileges on the composite login. Separate Trust API and worker roles also undergo the reachable-role check. This changes no SQL grants or canonical migrations.

The real canonical synthetic host started using the privately provisioned request login. PostgreSQL confirms core/Growth inherited rights, no Growth worker membership, no private Trust table SELECT, and bounded negative projection EXECUTE. A second private login bearing Growth worker membership was refused before listen. After removing that membership, a direct private Trust SELECT grant was also refused; the grant was removed and that probe login disabled.

A fresh Chromium sign-in through Pantopus development continuation loaded the saved resolved support case and its recipient's notice, with no legacy actor chooser or horizontal overflow. The screenshot was personally inspected. This confirms the saved state survives the role change, not a new decision. [Receipt](receipt.json) keeps the narrower limitations. The own API/web/database were stopped; data and private profiles remain outside Git. W1 has chosen a separate Growth/Content pool while retaining core `creator_runtime`, so its host does not enable this optional core override.
